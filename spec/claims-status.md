# Spec: 保険金請求ステータスのセルフサービス化

- 参照する intent: intent/claims-status.md（2026-06-02 に受理）
- レビュー: プロダクトオーナー
- 適用した Skill: secure-api-review

## 要件

- **R1** 認証済みの顧客が、自分が所有する請求のステータスを取得できる。
- **R2** レスポンスには請求の状態・次のステップ・その予定日を含む。
- **R3** 次の4状態を表現できる: received / assessing / awaiting_documents / settled
- **R4** 所有していない請求へのリクエストは、存在しない請求へのリクエストと区別がつかないこと。

## 設計

claims-api 上の読み取り専用エンドポイントとする。

    GET /v2/claims/{claim_id}/status

認証は既存のゲートウェイ JWT を `Authorization: Bearer <token>` として受け取る。新しい ID プロバイダを追加しないため、intent の制約を満たす。

エンドポイントは `claims_api.core.claims_core` 経由で claims-core を読み、個人情報を含まないレスポンスボディへ射影する。

    {"claim_id": "...", "state": "...", "next_step": "...",
     "expected_date": "YYYY-MM-DD"}

顧客氏名・住所など claims-core のレコードが持つ識別情報は、正常系で出力しないというだけでなく、射影の段階で落とす。これにより intent の「ポータルセッションに新たな個人情報を持ち込まない」という制約を満たす。

## intent から引き継いだ制約

- **C1** ポータルセッションに新たな個人情報を持ち込まない。許可リスト方式の射影と、許可リスト外のフィールドがレスポンスに含まれないことを検証するテストで担保する。
- **C2** 認証は既存のもののみ。リポジトリに既にあるゲートウェイ JWT 検証を再利用することで担保する。

## 設計中に判明した制約

- **C3** claims-core は 50 rps でレートリミットされており、オペレーターデスクトップと共有されている。ポータルに展開すると読み取り量が顧客数の分だけ増えるため、ポータルからのリクエストをそのまま claims-core へ通してはならず、エンドポイント側でキャッシュする。オペレーターにとってはデスクトップ側が正となるため、短い TTL で問題ない。

## 懸念事項（flag）

- CONCERN-1（起票時 open、担当: データ保護）。intent はポータルへの新たな個人情報の持ち込みを禁じている。`expected_date` は査定スケジュールから導出される値で、分類が定まっていない。顧客への開示が新規の開示にあたらないか確認が必要。→ 解決: 電話口では既に顧客へ伝えている情報であり、個人情報ではない。
- CONCERN-2（intent の未解決の問いから引き継ぎ）。第三者の損害査定人のアクセスは本変更のスコープ外とする。本エンドポイントの認可は請求の所有者判定のみで、査定人向けには別の認可モデルが必要になるため、別の intent として起票する。

## スコープ外

ポータルのフロントエンド。本 spec は API の契約のみを対象とする。ポータル側のパネルは、同じ intent に対する別の変更として扱う。
