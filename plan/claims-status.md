# Plan: 保険金請求ステータスのセルフサービス化

- 参照する spec: spec/claims-status.md
- 承認: 実装担当エンジニア
- 作成方法: Claude Code の plan mode で生成し、実装前に人が修正

## 変更するファイル

- claims_api/routes/status.py（新規）— エンドポイントと個人情報の射影
- claims_api/core/claims_core.py（新規）— TTL キャッシュ付き claims-core クライアント
- claims_api/auth.py（新規）— ゲートウェイ JWT の検証
- claims_api/app.py（新規）— アプリケーションファクトリとルート登録
- tests/test_status.py（新規）— 実装より先に書く検証

## 作業順

1. まず失敗するテストを書く。4つの状態、個人情報が出ないこと、401 の経路、キャッシュの挙動を対象とする。失敗する状態でコミットし、検証を緩めることで修正したことにできないようにする。
2. TTL キャッシュを持つ claims-core クライアントを追加する。
3. 既存認証の背後にエンドポイントを追加する。
4. アプリケーションにルートを登録する。

## リスク

- claims-core は 50 rps でレートリミットされ、オペレーターデスクトップと共有されている（spec C3）。キャッシュがないとポータル展開時に上限を食い潰し、より重要な利用者であるオペレーター側を劣化させる。したがってキャッシュは最適化ではなく制御であり、レビュー任せにせずテストで担保する。
- 個人情報の射影は許可リスト方式とする。除外リスト方式にすると、claims-core が将来フィールドを追加したときに黙って漏れる。tests/test_status.py で許可リストを検証する。

## 採らなかった選択肢

- ポータルから claims-core を直接呼ぶ。却下：レートリミットのある API に新たな利用者を増やすことになり、個人情報の射影がブラウザ側へ移って制約を強制できなくなる。
- ポータル側でキャッシュする。却下：claims-core を他の利用者から守れず、TTL がこのリポジトリでレビューできなくなる。

## 何をもって完了とするか

- `make test` がグリーンであること。
- tests/test_status.py が spec R3 の4状態、C1 の許可リスト、C2 の 401 経路、C3 のキャッシュをそれぞれ検証していること。
